Supplier Invitation workflow

4 statuses · 4 transitions

Statuses

StatusDescription
InvitedThe invitation has been sent to the supplier.
In ProgressThe invitation is active and the system is waiting for the supplier to accept it.
Invitation AcceptedThe supplier has accepted the invitation.
OverdueThe invitation has expired before being accepted.

Transition rules

FromToPerformed byNotes
Invited→In ProgressSystemInvitation becomes active and awaits supplier action
In Progress→Invitation AcceptedSupplierSupplier accepts the invitation
In Progress→OverdueSystemInvitation expires before being accepted
Overdue→InvitedRetailer / GreenstreetsA new invitation is sent to replace the expired one

Business rules

  • Suppliers cannot access the onboarding process until an invitation has been sent.
  • An invitation starts in Invited status and then moves to In Progress while awaiting supplier action.
  • Overdue is applied automatically when the invitation expiry date is reached before the supplier accepts it.
  • An expired invitation cannot be accepted.
  • To continue after an invitation becomes Overdue, a new invitation must be sent.
  • Status changes generate both an in-app notification and an email notification to the relevant users.
  • Invitation Accepted is the successful completion status for the invitation workflow.

Status flow

    direction TB
    [*] --> Invited
    Invited --> InProgress: System
    InProgress --> InvitationAccepted: Supplier
    InProgress --> Overdue: System
    Overdue --> Invited: Retailer / Greenstreets
    InvitationAccepted --> [*]
    InProgress: In Progress
    InvitationAccepted: Invitation Accepted
02

User Invitation workflow

6 statuses · 7 transitions

Statuses

StatusDescription
DraftThe user record has been created, but no invitation has been sent.
InvitedThe invitation has been sent to the user, but the invitation is still pending acceptance.
ActiveThe user has accepted the invitation and the account is active.
ExpiredThe user did not accept the invitation before the invitation expiry date.
ResendA new invitation has been sent after a previous invitation expired or was not accepted.
DeactivatedThe user's account has been deactivated and can no longer be used to access the platform.

Transition rules

FromToPerformed byNotes
Draft→InvitedAdminInitial invitation is sent to the user
Invited→ActiveUserUser accepts the invitation
Invited→ExpiredSystemInvitation expires before being accepted
Expired→ResendAdminA new invitation is sent
Resend→ActiveUserUser accepts the resent invitation
Resend→ExpiredSystemResent invitation expires before being accepted
Active→DeactivatedAdminUser account is deactivated

Business rules

  • Users cannot access the platform until they accept an invitation.
  • Invitations automatically move to Expired when the expiry date is reached.
  • Expired invitations cannot be accepted.
  • Administrators can resend an expired or unaccepted invitation.
  • When an invitation is resent, the status changes to Resend.
  • Status changes generate both an in-app notification and an email notification to the relevant users.
  • Active is the successful completion status for the invitation process.
  • Deactivated is a terminal status and prevents further access to the platform.

Status flow

stateDiagram-v2
    direction TB
    [*] --> Draft
    Draft --> Invited: Admin
    Invited --> Active: User
    Invited --> Expired: System
    Expired --> Resend: Admin
    Resend --> Active: User
    Resend --> Expired: System
    Active --> Deactivated: Admin
    Deactivated --> [*]
03

Document workflow

4 statuses · 5 transitions

Statuses

StatusDescription
PendingThe document has been submitted and is waiting for approval from the Retailer Admin / Greenstreets team.
ApprovedThe document has been reviewed and approved by the Retailer Admin / Greenstreets team.
Not ApprovedThe document has been reviewed and was not approved. The document may require updates or replacement.
ExpiredThe document expired before it was approved.

Transition rules

FromToPerformed byNotes
Pending→ApprovedRetailer Admin / GreenstreetsThe document review is completed successfully.
Pending→Not ApprovedRetailer Admin / GreenstreetsThe document review failed or additional information is required.
Pending→ExpiredSystemThe document expiry date is reached before approval.
Not Approved→PendingSupplierThe supplier uploads an updated document for review.
Expired→PendingSupplierThe supplier uploads a renewed/replacement document for review.

Business rules

  • Documents are initially created in Pending status.
  • Documents in Pending status are awaiting approval from the Retailer Admin / Greenstreets team.
  • A document moved to Not Approved should include a reason explaining why it was rejected.
  • A document automatically moves to Expired when the expiry date is reached before approval.
  • Suppliers can upload a replacement or updated document after a document becomes Not Approved or Expired.
  • Status changes generate both an in-app notification and an email notification to the relevant users.
  • Approved is the final successful status in the workflow.
  • Documents in Approved status are considered valid and can be used for compliance purposes.
  • Documents in Not Approved or Expired status cannot be used for compliance purposes.

Status flow

stateDiagram-v2
    direction TB
    [*] --> Pending
    Pending --> Approved: Retailer Admin / Greenstreets
    Pending --> NotApproved: Retailer Admin / Greenstreets
    Pending --> Expired: System
    NotApproved --> Pending: Supplier
    Expired --> Pending: Supplier
    Approved --> [*]
    NotApproved: Not Approved
04

Products Page (Retailer Portal) workflow

3 statuses · 3 transitions

This status is derived automatically from the statuses of the product's packaging components, so transitions are listed by trigger rather than by actor.

Statuses

StatusDescription
PendingThe supplier has not started providing any packaging component information.
IncompleteThe supplier has started providing packaging component information, but one or more required packaging components are still missing or not yet approved.
CompleteAll required packaging components have been provided and approved.

Transition rules

FromToTriggerNotes
Pending→IncompleteSupplier starts providing packaging component informationAt least one required packaging component has been created or submitted.
Incomplete→CompleteAll required packaging components are approvedEvery required packaging component for the product has reached the Approved status.
Complete→IncompleteAn approved packaging component is returned, cancelled, or no longer approvedThe product can no longer be considered complete because a required component is no longer approved.

Business rules

  • A product starts in Pending when no packaging component information has been provided by the supplier.
  • A product moves to Incomplete as soon as the supplier starts providing packaging component information.
  • A product remains Incomplete until all required packaging components are approved.
  • A product moves to Complete only when every required packaging component is in the Approved state.
  • If any approved packaging component is later changed, returned for updates, or loses its approval status, the product returns to Incomplete.
  • The product status is derived automatically from the status of its associated packaging components.

Status flow

stateDiagram-v2
    direction TB
    [*] --> Pending
    Pending --> Incomplete: Supplier starts
    Incomplete --> Complete: All required approved
    Complete --> Incomplete: Component loses approval
    Complete --> [*]
05

Packaging Component workflow

4 statuses · 5 transitions

Statuses

StatusDescription
IncompleteThe packaging component is missing required information or details.
Review NeededThe supplier has provided the packaging component details and the Retailer Admin/Greenstreets team must review and approve them.
CompleteThe packaging component has been reviewed and approved by the Retailer Admin/Greenstreets team.
Needs ChangingThe packaging component has been reviewed and requires updates before it can be approved.

Transition rules

FromToPerformed byNotes
Incomplete→Review NeededSupplierAll required component details have been provided and submitted for review.
Review Needed→CompleteRetailer Admin / GreenstreetsThe component has been reviewed and approved.
Review Needed→Needs ChangingRetailer Admin / GreenstreetsThe component requires updates. A reason should be provided.
Needs Changing→Review NeededSupplierThe supplier has updated the component and resubmitted it for review.
Complete→Needs ChangingRetailer Admin / GreenstreetsAn approved component requires further updates or corrections. (Exception path)

Business rules

  • Suppliers can edit packaging components while they are in Incomplete or Needs Changing status.
  • Required validation rules must pass before a component can move to Review Needed.
  • A component in Review Needed can only be approved or returned for changes by the Retailer Admin/Greenstreets team.
  • Needs Changing must include a reason explaining what requires correction.
  • When a component is moved to Needs Changing, the supplier receives both an in-app notification and an email notification.
  • Status changes generate both an in-app notification and an email notification to the relevant users.
  • Complete is the final successful status unless the Retailer Admin/Greenstreets team later requires updates.

Status flow

stateDiagram-v2
    direction TB
    [*] --> Incomplete
    Incomplete --> ReviewNeeded: Supplier
    ReviewNeeded --> Complete: Retailer Admin / Greenstreets
    ReviewNeeded --> NeedsChanging: Retailer Admin / Greenstreets
    NeedsChanging --> ReviewNeeded: Supplier
    Complete --> NeedsChanging: Retailer Admin / Greenstreets
    Complete --> [*]
    ReviewNeeded: Review Needed
    NeedsChanging: Needs Changing

Exception path: Complete → Needs Changing → Review Needed.

Packaging Component Status Field workflow

7 statuses · 11 transitions

Statuses

StatusValueDescription
Awaiting Supplierawaiting_supplier / REQUESTEDThe retailer has defined the expected packaging component requirement and is awaiting supplier fulfilment.
DraftdraftThe supplier has started fulfilling the requirement (linking or creating data) but has not yet submitted it.
SubmittedsubmittedThe supplier has fulfilled and submitted the packaging component specification.
Pending Reviewpending_reviewThe submission is in the retailer/Greenstreets review queue awaiting evaluation.
Approvedapproved / FULFILLEDThe component details have been accepted by the retailer and confirmed for the product packaging version.
Changes Requestedchanges_requestedThe retailer has rejected/returned the component with a returnReason for correction.
Not Requirednot_required / CANCELLEDThe retailer has marked the requirement as cancelled or no longer required.

Transition rules

FromToPerformed byNotes
Awaiting Supplier→DraftSupplierSupplier begins fulfilling the requirement
Draft→SubmittedSupplierSupplier completes the component and submits it
Submitted→Pending ReviewSystemSubmission enters the retailer review queue
Pending Review→ApprovedRetailer / GreenstreetsReview completed successfully
Pending Review→Changes RequestedRetailer / GreenstreetsReturn reason is required
Changes Requested→DraftSupplierSupplier updates the component and resubmits
Awaiting Supplier→Not RequiredRetailer / GreenstreetsRequirement is cancelled before completion
Draft→Not RequiredRetailer / GreenstreetsRequirement is cancelled while in progress
Submitted→Not RequiredRetailer / GreenstreetsRequirement is cancelled after submission
Pending Review→Not RequiredRetailer / GreenstreetsRequirement is cancelled during review
Approved→Not RequiredRetailer / GreenstreetsApproval is revoked and the requirement is cancelled

Business rules

  • Suppliers can edit component data only while the component is in Draft status.
  • Required validation rules must pass before a component can move from Draft to Submitted.
  • A submission automatically moves from Submitted to Pending Review.
  • Retailer/Greenstreets reviewers can move a component from Pending Review to Approved or Changes Requested.
  • Changes Requested must include a returnReason.
  • When a component is returned, the supplier receives both an in-app notification and an email notification.
  • Status changes generate both an in-app notification and an email notification to the relevant users.
  • Human approval is required before DoC generation.
  • Approved is the final successful status in the workflow unless the retailer explicitly marks the requirement as Not Required.
