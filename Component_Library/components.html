GreenStreets component library

Every component used across the four GreenStreets portals, rendered by the actual prototype stylesheets. Each specimen carries the markup that produces it, the classes to port, the stylesheet it lives in, and links to the pages it appears on.

One specimen per style, base elements first. Anything labelled Base is one component with one class contract — port it as a component. Composed means base elements plus typography, carrying no CSS of its own — port it as a pattern, and its parts are listed as links. Where the codebase has several classes for the same style, only one appears here and the tooltip names the rest. Hover the i for the rules; hover a specimen for Copy.

Porting notes. These prototypes are vanilla HTML/CSS/JS with no build step, so behaviour that a React port would express as component state is currently a class toggle plus a global function (.on, .open, .active, go('sN')). Treat the markup + class contract as the spec and the inline onclick as a note about intent. Where a component is generated by JS rather than authored (data grids, AI review fields, packaging detail sections, tour bubbles), the specimen shows the DOM shape that JS produces and the tooltip names the file that produces it.

Typography

There is no h1–h6 scale here — headings are components (.pg-title, .grp-hdr, .sec-lbl). Keep the HTML heading level correct for the outline and let the class carry the size.

Buttons

Three variants, three sizes. Everything else in the codebase that looks like a fourth button is .btn-g renamed — the tooltips name the duplicates so the port can collapse them.

Form inputs

One primitive, .fi, wrapped by .fgrp (label + control + hint). Native <select> popups cannot be themed, so the theme JS swaps every select.fi for a themed one and keeps the real element for its value — the selects below are those replacements.

Selection controls

The packaging schema picks the control: a two-value vocabulary becomes a switch, a short list a segmented control, a long list a select, a 0–100 number a slider. That mapping lives in gs-pkg-controls.js.

Alerts & feedback

Banners for standing conditions, toasts for what just happened, inline notes for a specific piece of data. Each one says what is wrong and what to do about it.

Cards & surfaces

One glass surface — translucent fill, 1px border, backdrop blur — shaped for different payloads. .grp is the workhorse; the rest are the same recipe.

Tables & the data-grid toolkit

Author a plain table.tbl with a .filter-toolbar above it and initListings() upgrades it into a real grid: filters, density, column chooser, CSV export, bulk select, pagination, sticky header, empty state and roving keyboard focus. The first specimen is that toolkit, live.

Modals & dialogs

Read this section top to bottom. The dialog surface and the dialog heading are the base elements; everything after them is those two plus buttons.

Pills, badges & status

Status is the most repeated idea in the product. The rule: a status is always a pill with a word in it — never a bare dot, never colour alone.

Progress, steps & meters

Compliance is a completion problem, so most screens answer “how far along is this?”. Meters show a proportion, steppers show position — both always pair the visual with the raw figures.

App shells

Two shells only: the three staff portals use .app-body > .sidebar + .main; the Supplier Portal has no sidebar and uses .pshell > .ph + .pbody.

Navigation

Note the active state worth copying exactly: the sidebar accent bar sits on the right edge of the item, pulling the eye toward the content rather than away from it.

Menus & dropdowns

Anchored popovers that are not dialogs — no scrim, close on click-outside, never trap focus. Pinned open here so they can be inspected.

Tooltips & hovercards

Three weights: a native title for a label, a small tooltip for a figure, a hovercard when the answer is a table of values. Nothing essential lives only in a hover.

Packaging data capture

None of these fields are hand-written. The nine sections, their labels, their vocabularies, what is mandatory and how each maps to the client spreadsheet all come from gs-schema.js, and every portal renders from it. A hand-typed label or an off-vocabulary value fails silently, at export time.

AI upload & review

Upload a spec sheet, let the model extract the schema fields, then review every value before accepting. Generated by air-review.js from the same schema as the manual form, so both produce the same object. The model proposes; the supplier attests.

Documents

A document is not a file attachment here — it is referenced by many packaging components, and its expiry can invalidate a DoC. Hence the two view modes, the preview and the expiry tracking.

Notifications

The busiest information design in the product: severity stripe, severity icon, title with timestamp, a message that quantifies the problem, inline actions, type pill.

Onboarding, invites & import

Every invite offers a copyable link and an email send, because a retailer’s supplier contacts are spread across a dozen inboxes.

Login & auth

One login card across all four portals: a two-zone glass panel over an optional photographic background.

Timeline & audit

Compliance work is contested after the fact, so “who changed what, when, and through which portal” is a first-class view.

Guided tours

A cross-page coach tour: a bubble anchored to a real control, a scrim dimming everything else, and a highlight ring on the target. It survives navigation, which is what makes it usable here.

Design tokens

Every colour, radius, shadow and spacing step is a custom property in :root. The light theme does not restyle components — it re-declares these same tokens under body.lt. Port this layer first.

Theming & appearance

A light page is body.lt plus greenstreets-light.css loaded last, and nothing else. The prototypes need a -Light.html twin per page because they have no router; this catalogue (one file, both themes) is the shape to copy.

Motion & interaction

Global effects, wired once with no per-component work and driven by :root tokens. They are load-bearing, not decoration: the focus ring is the only focus indicator on a field, and the ripple is the only press feedback on a listing row.

Prototype-only scaffolding — do not port

The seams a Next.js port removes. Listed so nobody mistakes them for product UI — recognising them is the difference between porting the design and porting the workaround.
